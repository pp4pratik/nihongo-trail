# Contributing to Nihongo Trail

This is a solo-maintained, personal-learning-tool-turned-open-source project. Contributions
are welcome, but the project has some specific working rules that come from
[`docs/REQUIREMENTS.md`](docs/REQUIREMENTS.md) and [`CLAUDE.md`](CLAUDE.md) — read those
before proposing a change, especially if it touches the data model or curriculum sequencing.

## Setup

```bash
npm install
npm run content:build
npm run dev
```

Requires Node ≥ 20 (matches [`ts-fsrs`](https://github.com/open-spaced-repetition/ts-fsrs)'s
own requirement).

## Before opening a PR

```bash
npm run lint
npm run typecheck
npm test
npm run build   # confirms the production build + PWA service worker still generate cleanly
```

All four should pass. CI runs the same three checks (lint, typecheck, test) on every push.

## The rules that matter most

**Never hand-edit anything in `public/content/`.** It's entirely generated by scripts in
`scripts/ingest/`, run via `npm run content:build`. If you need different content, change
the generator (or the hand-authored source it reads from) and regenerate.

**Build phase-by-phase.** See `docs/REQUIREMENTS.md` §16. Don't start Phase N+1 work until
Phase N's acceptance criteria pass. The project is currently on Phase 1 (Kana MVP) —
complete; see the README for status.

**The data model in §12 of the requirements doc is contractual.** Changing a type in
`src/types/` requires a note in [`docs/DECISIONS.md`](docs/DECISIONS.md) explaining why —
several existing entries there are examples of exactly this (e.g. `SrsCard.learningStep`,
`ResolvedExercise.groupId`). Follow that pattern: what changed, why the spec didn't already
cover it, what section it affects.

**Never break the resume contract** (§10.4). If you touch the session engine
(`src/features/session/`) or the persistence layer (`src/storage/`), run the resume test
specifically before anything else:

```bash
npx vitest run tests/integration/session/resume.spec.ts
```

This is the single most important test in the project — it verifies that killing the tab
mid-lesson at any point loses zero answers and reproduces the exact same exercise sequence
on reopen. If a change breaks it, that's a real regression, not a flaky test.

## Testing philosophy

Tests live next to what they cover, split into `tests/unit/` (pure logic, components) and
`tests/integration/` (storage layer, session engine against a real — `fake-indexeddb` —
IndexedDB). New logic should ship with tests; new UI should be checked against the running
app in a browser, not just unit-tested — several real bugs in this codebase's history were
only caught by actually clicking through the app (see the Phase 1 commit message and
`docs/DECISIONS.md` for examples), not by the test suite alone.

## Code style

- No comments explaining *what* code does — names should do that. Comments are for *why*:
  a non-obvious constraint, a spec citation, a workaround for a specific bug.
- No premature abstraction. Three similar lines beat a speculative helper function.
- Prefer the smallest diff that correctly and completely solves the problem — but "smallest"
  doesn't mean "shortcut." If a change needs full test coverage to be correct, write the full
  test coverage.

## Questions

Open an issue. For anything touching curriculum sequencing (§5.5) or the data model (§12),
it helps to reference the specific section of `docs/REQUIREMENTS.md` you're working against.
