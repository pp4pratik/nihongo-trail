## 1. Product vision

### 1.1 One-line description

A single-user, offline-capable web app that takes a complete beginner from zero Japanese to solid JLPT N5 competence through short daily sessions, using Duolingo-style lesson units for teaching and a spaced-repetition engine for retention.

### 1.2 The problem being solved

Existing options each fail in a specific way for this use case:

- **Duolingo Japanese** teaches enjoyably but its retention model is weak, its kanji coverage is shallow, and it does not let you see or control what you actually know.
- **Anki** has excellent retention but zero teaching, zero structure, and a high setup burden. It assumes you already know what to study.
- **WaniKani** is excellent for kanji but deliberately ignores grammar and does not teach kana.
- **Textbooks (Genki, Minna no Nihongo)** are structurally sound but have no scheduling, no feedback loop, and no way to resume mid-thought.

Nihongo Trail combines the teaching structure of a course, the retention engine of Anki, and the session design of Duolingo — for one learner, with full ownership of the data.

### 1.3 Goals

| # | Goal | How it is measured |
|---|---|---|
| G1 | Take an absolute beginner to JLPT N5 reading/listening competence | ~100 kanji, ~800 vocabulary items, ~80 grammar points mastered (§5.6) |
| G2 | A session must be startable and finishable in 10–15 minutes | Median session duration 10–15 min (§4.2) |
| G3 | Never lose a learner's place | Resume contract §10.4; zero data-loss incidents |
| G4 | Work fully offline after first load | Lighthouse PWA offline check passes |
| G5 | Retention, not just exposure | 90-day retention of "mastered" items ≥ 85% (§4.2) |
| G6 | Make daily practice feel worth returning to | Streak sustained; §9 gamification |

### 1.4 Non-goals (explicitly out of scope for v1)

- Speaking practice / pronunciation scoring via microphone (deferred; see §18.3)
- Handwriting recognition or handwriting input
- Multi-user accounts, social features, leaderboards, friends
- Any content beyond N5 in v1 (architecture must not block N4+; see §5.7)
- Monetisation, ads, analytics SDKs, telemetry to third parties
- Native app store distribution (PWA install is sufficient)
- Teaching Japanese output/composition beyond sentence-assembly exercises

### 1.5 Design principles

1. **Local-first.** The app works with no network and no account. Sync, when added, is an enhancement, never a dependency.
2. **The learner owns the data.** One-click JSON export at all times. No lock-in.
3. **Teach then test.** Nothing appears in a review queue that has not been explicitly introduced first.
4. **Interruption is normal.** Every screen is resumable. Closing the tab mid-exercise loses nothing.
5. **Honesty over flattery.** Progress indicators reflect real recall probability, not items-touched.
6. **No dark patterns.** Hearts limit a *lesson*, never *review*. Streak freezes are generous. Nothing is engineered to induce guilt.

## 2. Target user

A single user profile — the app is built for one person and does not need to generalise.

| Attribute | Value |
|---|---|
| Japanese level at start | Absolute beginner. Cannot read hiragana or katakana. |
| Native/fluent languages | English (UI language, meaning language) |
| Devices | Primarily phone (portrait, one-handed), sometimes laptop |
| Study commitment | 10–15 minutes/day, casual, most days |
| Motivation | Personal interest; JLPT N5 as a concrete milestone, not a hard deadline |
| Technical ability | High — comfortable running scripts, editing JSON, self-hosting |
| Context of use | Commute, break, before bed. Often with sound off. Often interrupted. |

**Implications that drive requirements:**

- Sound-off usage is common → every audio exercise must have a non-audio fallback path (§11.5).
- One-handed portrait phone usage → all primary tap targets in the bottom 60% of the viewport (§14.2).
- Frequent interruption → aggressive checkpointing (§10.3).
- Casual pace → new-item introduction must be throttled so review load stays under the daily time budget (§8.7).

## 4. Success metrics

### 4.1 The primary metric

**Ninety-day retention of items marked "mastered."** Everything else is secondary. If the app produces streaks and XP but the learner cannot read a word they "learned" three months ago, it has failed.

Measured by: a monthly automatic audit that samples 30 items whose last review was 90+ days ago and reports the first-attempt correct rate on their next review. Target ≥ 85%.

### 4.2 Supporting metrics

| Metric | Target | Source |
|---|---|---|
| Median session duration | 10–15 min | Session log (§12.6) |
| Daily review queue size | ≤ 60 items at steady state | Computed nightly (§8.7) |
| First-attempt accuracy in review | 80–90% | Review log. Below 80% → introduction rate too high. Above 92% → too conservative, can accelerate. |
| Lesson completion rate | ≥ 90% of started lessons finished within 24h | Session log |
| Streak length | Informational only — never optimised for | Progress store |
| Time from app open to first exercise | < 3 seconds on 4G | Performance budget §15.2 |

### 4.3 Anti-metrics

Deliberately **not** tracked or optimised: total time in app, sessions per day, notification click-through. Optimising these produces an app that wastes the learner's time.

## 5. Curriculum design

### 5.1 Structure

Four levels of hierarchy:

```
Stage  →  Unit  →  Lesson  →  Exercise
```

| Level | Size | Purpose |
|---|---|---|
| **Stage** | 4 total | Broad phase of the journey. Gates content unlocks. |
| **Unit** | ~10–20 per stage | A coherent theme (e.g. "Family", "Te-form"). Unit test at the end. |
| **Lesson** | 4–6 per unit | One 10–15 min sitting. The atomic unit of progress. |
| **Exercise** | 12–18 per lesson | A single question/answer interaction. |

**Rule:** a lesson is always completable in a single sitting at the target pace. If a lesson would exceed 18 exercises, split it.

### 5.2 Stage map

| Stage | Name | Content | Est. duration at 10–15 min/day |
|---|---|---|---|
| **0** | Kana Foundations | Hiragana, then katakana. No kanji, no grammar. | 4–6 weeks |
| **1** | First Words | ~200 vocab, ~25 kanji, core particles (は/が/を/に/で/と/も), です/ます, basic adjectives | 8–10 weeks |
| **2** | Everyday Japanese | ~350 vocab, ~45 kanji, verb conjugation (て-form, past, negative), counters, time expressions | 14–18 weeks |
| **3** | N5 Consolidation | ~250 vocab, ~35 kanji, remaining N5 grammar, mixed reading + listening comprehension | 12–16 weeks |

Total: roughly **9–12 months** at the stated pace, consistent with published estimates for N5 (see §5.6).

### 5.3 Stage 0 in detail — Kana Foundations

This stage is fully specified because it is the highest-risk part of the curriculum: if kana does not stick, nothing else works.

**Scope per script:**

| Set | Count | Example |
|---|---|---|
| Basic (gojūon) | 46 | あ い う え お か き … |
| Dakuten / handakuten (voiced) | 25 | が ぎ ぐ … ば ぱ … |
| Yōon (digraphs) | 33 | きゃ きゅ きょ … |
| Small tsu (っ) + long vowels | special rules | かった、こうこう |

**Introduction order** — by row (gyō), 5 characters per lesson:

```
Lesson 1: あ い う え お
Lesson 2: か き く け こ
Lesson 3: review 1–2 (mixed)
Lesson 4: さ し す せ そ    ← note し = "shi", not "si"
Lesson 5: た ち つ て と    ← note ち = "chi", つ = "tsu"
Lesson 6: review 4–5
...
```

Every third lesson is a mixed review of the preceding two. Irregular readings (し shi, ち chi, つ tsu, ふ fu, ん n) are called out explicitly in the teaching card.

**Confusable pairs** — the app must maintain an explicit confusion-pair table and deliberately generate distractor options from it, because random distractors will not surface these:

| Script | Confusable set |
|---|---|
| Hiragana | め/ぬ, は/ほ/ま, れ/わ/ね, さ/き, る/ろ, い/り, つ/し |
| Katakana | シ/ツ, ソ/ン, ク/ワ/ケ, ア/マ, ス/ヌ, チ/テ |
| Cross-script | り/リ, か/カ, へ/ヘ, ん/ソ |

**Katakana gate:** katakana lessons unlock only when hiragana average FSRS retrievability ≥ 0.85 across all 46 basic characters. Rationale: learning both scripts simultaneously causes heavy interference for beginners.

**Stage 0 exit criteria:** all 104 hiragana + 104 katakana forms at FSRS state `Review` with retrievability ≥ 0.9, and a timed recognition test at ≥ 95% accuracy with median response < 2s.

### 5.4 Stage 1–3 unit template

Each unit follows a fixed shape so lesson generation can be automated:

| Lesson | Type | Content |
|---|---|---|
| 1 | **Vocabulary intro** | 5 new words, taught then drilled |
| 2 | **Kanji intro** | 2–3 new kanji: meaning, on/kun readings, stroke order, example words |
| 3 | **Grammar intro** | 1 grammar point: explanation card + 12 pattern exercises |
| 4 | **Mixed practice** | Combines lessons 1–3 with items from previous units |
| 5 | **Listening** | Audio-first exercises on unit content |
| 6 | **Unit test** | 20 exercises, no hints, no hearts refill. Pass = 85%. |

**Unit test failure:** does not lock progress. It marks the unit "needs review", schedules a targeted review lesson, and lets the learner continue. Blocking progress on a test creates a dead end for a solo learner.

### 5.5 Sequencing rules (constraints the content generator must satisfy)

These are hard invariants and should be enforced by a validation script (§6.6):

1. **No unintroduced characters.** A vocabulary item may not appear before every kana in it has been taught. Kanji in a word must either be taught already or be displayed with furigana.
2. **Kanji before compound.** A kanji-containing word may only appear kanji-first after the kanji itself has been introduced; before that it appears in kana.
3. **Grammar needs vocabulary.** A grammar exercise may only use vocabulary already introduced, plus at most one new supporting word (which is then registered as introduced).
4. **Frequency-first ordering.** Within any constraint set, higher-frequency items (JMdict `common` tags: `news1`, `ichi1`, `spec1`, `spec2`, `gai1`) come first.
5. **Spacing of confusables.** Two items in the same confusion set are never introduced in the same lesson.
6. **Sentence eligibility.** An example sentence may be used in an exercise only if ≥ 90% of its tokens are already introduced; the remainder must be glossed inline.

### 5.6 N5 scope targets and their provenance

The JLPT has **not published an official vocabulary or kanji list since the 2010 exam revision** ([Wikibooks JLPT Guide](https://en.wikibooks.org/wiki/JLPT_Guide/JLPT_N5_Kanji)). All targets below are community-consensus estimates, and the app should treat them as guidance rather than a fixed syllabus.

| Item | Target | Source and caveat |
|---|---|---|
| Kanji | ~100 | [Japonin](https://www.japonin.com/jlpt-n5-present.html) states "approximately 100 basic characters." Wikibooks notes its own list has 81 entries and estimates ~103 in the current exam. Plan for 100–105. |
| Vocabulary | ~800 | Japonin: "around 800–900 essential words." Community lists (JLPTsensei, Migaku) fall in the same range. |
| Grammar points | ~80 | Community lists (e.g. [JLPTsensei N5 grammar list](https://jlptsensei.com/jlpt-n5-grammar-list/)) cluster around 70–90 depending on how patterns are split. Unverified precise count — treat 80 as a planning figure, not a fact. |
| Study time to N5 | 3–6 months at "steady study" | [Japonin](https://www.japonin.com/jlpt-n5-present.html). At the casual 10–15 min/day pace chosen here, 9–12 months is the realistic figure. |

**Implementation note:** store the JLPT level as a *tag* on each item, sourced from KANJIDIC2's `jlpt` field where present (which reflects the pre-2010 four-level test) plus a maintained override list. Do not architect around JLPT levels being authoritative.

### 5.7 Forward compatibility

Nothing in the data model may hard-code "N5". Stages, units and lessons are data, not code. Adding Stage 4 (N4) must require only new content JSON plus a manifest entry — no schema change and no code change.

## 6. Content data sources and ingestion

### 6.1 Source datasets

All content is derived from openly licensed datasets, processed at build time into app-specific JSON, and bundled with the app for offline use.

| Dataset | Provides | Licence | Notes |
|---|---|---|---|
| **JMdict** (via [jmdict-simplified](https://github.com/scriptin/jmdict-simplified)) | Word entries: kanji forms, kana readings, English senses, part of speech, commonness tags | [EDRDG Licence](https://www.edrdg.org/edrdg/licence.html) — attribution required | jmdict-simplified ships pre-built JSON releases, refreshed weekly (Mondays). Use the **common-only, English** variant to cut size dramatically. |
| **KANJIDIC2** (via jmdict-simplified) | Per-kanji: meanings, on/kun readings, stroke count, grade, frequency rank, JLPT level, radical | **CC BY-SA 4.0** | Confirmed by the jmdict-simplified README. |
| **KanjiVG** | Stroke-order SVG paths, stroke direction, component/radical decomposition | **CC BY-SA 3.0** | Used for stroke-order animation (§7.9). |
| **Tatoeba** | Japanese example sentences with English translations | Primarily **CC BY 2.0 FR**; a subset is **CC0 1.0** | Sentence audio exists but its licence is chosen per contributor and may be unspecified — see §11.2. |
| **Kradfile / Radkfile** (via jmdict-simplified) | Kanji ↔ radical decomposition | EDRDG Licence | Optional; powers a radical-based kanji search if built. |

**Licence obligations that must be met (non-negotiable):**

- EDRDG requires visible attribution to the Electronic Dictionary Research and Development Group for JMdict/JMnedict/Kradfile-derived data.
- KANJIDIC2 (CC BY-SA 4.0) and KanjiVG (CC BY-SA 3.0) require attribution **and** share-alike on derivative data files.
- Tatoeba CC BY 2.0 FR requires attribution.
- Full attribution text is specified in **Appendix A** and must render on an in-app "Credits" screen reachable from Settings, plus a `NOTICE` file in the repo.

Because share-alike applies to the *derived content files*, keep generated content in a separate directory (`public/content/`) with its own `LICENSE` file, distinct from the application source. This lets the app code carry whatever licence you prefer while the data stays compliant.

### 6.2 Ingestion pipeline

Build-time only. Never runs in the browser.

```
scripts/ingest/
├── 00-download.ts       # fetch source archives to .cache/ (idempotent, checksummed)
├── 01-parse-jmdict.ts   # JMdict common+eng → normalised word records
├── 02-parse-kanjidic.ts # KANJIDIC2 → kanji records
├── 03-parse-kanjivg.ts  # KanjiVG SVG → stroke path arrays
├── 04-parse-tatoeba.ts  # sentences + links + jpn/eng pairing
├── 05-build-curriculum.ts # apply §5.5 sequencing rules → stages/units/lessons
├── 06-validate.ts       # invariant checks (§6.6) — exits non-zero on violation
└── 07-emit.ts           # write sharded JSON + manifest to public/content/
```

Run via `npm run content:build`. Output is committed to the repo so the app is buildable without network access.

### 6.3 Output shape

Content is **sharded** so the app never loads the whole dictionary:

```
public/content/
├── manifest.json           # version, checksums, shard index, dataset versions
├── curriculum.json         # stage/unit/lesson tree (~200 KB) — always loaded
├── kana.json               # all kana + confusion pairs (~40 KB) — always loaded
├── words/
│   ├── shard-000.json      # ~100 words each, referenced by lesson
│   └── ...
├── kanji/
│   └── shard-000.json
├── sentences/
│   └── shard-000.json
└── strokes/
    └── {codepoint}.json    # lazy-loaded, only when stroke animation is shown
```

**Budget:** initial load (curriculum + kana + first shard) must stay under 500 KB gzipped. Everything else is fetched on demand and cached by the service worker.

### 6.4 Content versioning

`manifest.json` carries a `contentVersion` (semver). The app stores the content version it last synced against. On mismatch:

- **Patch** (typo fix, better translation) → apply silently.
- **Minor** (new items added) → apply; new items enter the pool as un-introduced.
- **Major** (item IDs changed or removed) → run a migration (§12.9). Progress records for removed items are archived, never deleted.

**Item IDs must be stable and content-derived**, not sequential:

```
kana:hiragana:あ
word:jmdict:1310920          # JMdict entry sequence number
kanji:U+65E5                 # Unicode codepoint
grammar:n5:te-form-request   # hand-authored stable slug
sentence:tatoeba:112345
```

Never renumber. If a source entry disappears upstream, tombstone the ID rather than reusing it.

### 6.5 Hand-authored content

Three things cannot come from open datasets and must be written by hand (or generated once and reviewed):

1. **Grammar explanation cards** — ~80 short explanations, 100–200 words each, with 2–3 example sentences. This is the single largest authoring task. Budget it explicitly.
2. **Kanji mnemonics** — optional but high-value. Story linking radical components to meaning.
3. **Unit themes and ordering** — the pedagogical spine that the generator fills in.

Store these in `content/authored/` as Markdown with YAML frontmatter, and ingest them in step `05`. Keeping them in Markdown means they are diffable and editable without touching JSON.

### 6.6 Validation invariants

`06-validate.ts` must fail the build if any of these are violated:

- Every lesson references only item IDs that exist.
- Every item is introduced exactly once across the whole curriculum.
- No lesson exceeds 18 exercises.
- Sequencing rules §5.5 (1)–(6) hold for every lesson.
- Every word has at least one reading and one English sense.
- Every audio-required exercise has a resolvable audio source or a documented TTS fallback.
- No orphan items (present in shards but referenced by no lesson).
- Every confusion-pair member is introduced in a different lesson from its partner.

## 7. Exercise types

Fifteen exercise types. Each specifies its prompt, input mode, grading rule, and which item types it applies to.

### 7.0 Common contract

Every exercise implements the same interface (see §12.5 for the type):

- **Prompt** — what the learner sees/hears
- **Input** — how they answer
- **Grading** — correct / incorrect / partially correct
- **Feedback** — what is shown after answering
- **SRS rating** — how the result maps to an FSRS rating (§8.4)
- **Applies to** — which item types can generate it

### 7.1 Recognition (multiple choice)

| | |
|---|---|
| Prompt | Japanese item (kana/word/kanji), optionally with audio |
| Input | Tap one of 4 options in English |
| Distractors | 1 from the confusion set if one exists, 2 from the same lesson/unit, remainder from same part-of-speech pool |
| Grading | Exact match |
| Applies to | Kana, word, kanji |

### 7.2 Recall (multiple choice, reversed)

| | |
|---|---|
| Prompt | English meaning |
| Input | Tap one of 4 Japanese options |
| Distractors | Same-reading or visually similar items preferred |
| Grading | Exact match |
| Applies to | Kana, word, kanji |

### 7.3 Typing — romaji to kana

| | |
|---|---|
| Prompt | Kana character or word displayed |
| Input | Type romaji; app converts to kana live (custom IME, §15.5) |
| Grading | Normalised comparison — accept both `shi`/`si`, `tsu`/`tu`, `fu`/`hu`, `ji`/`zi`, `n`/`nn` |
| Feedback | On error, show the expected kana and the accepted romaji variants |
| Applies to | Kana, word |

### 7.4 Typing — meaning to Japanese

| | |
|---|---|
| Prompt | English meaning + part of speech |
| Input | Type in kana (romaji auto-converted) |
| Grading | Accept any valid reading of the target word. Accept kana-only answers even when the word is normally written in kanji. |
| Applies to | Word |

### 7.5 Typing — Japanese to meaning

| | |
|---|---|
| Prompt | Japanese word |
| Input | Free-text English |
| Grading | Fuzzy: normalise case/punctuation/articles; accept any listed JMdict gloss; Levenshtein distance ≤ 2 counts as correct with a "close — here's the exact wording" note |
| Applies to | Word, kanji meaning |

### 7.6 Sentence building (word bank)

| | |
|---|---|
| Prompt | English sentence to translate |
| Input | Tap tiles from a shuffled word bank to assemble the Japanese sentence |
| Distractor tiles | 2–3 plausible extras — especially wrong particles, which is the highest-value drill in early Japanese |
| Grading | Exact token sequence. If multiple valid orders exist, the content file lists all accepted orders. |
| Applies to | Grammar, sentence |

### 7.7 Fill in the blank

| | |
|---|---|
| Prompt | Japanese sentence with one token replaced by `___`, plus English translation |
| Input | 4 options (tap) or free typing, depending on difficulty setting |
| Grading | Exact match on the blank |
| Applies to | Grammar, particle drills, conjugation |

### 7.8 Listening — transcribe

| | |
|---|---|
| Prompt | Audio only (word or sentence), replay button, 0.75× slow-replay button |
| Input | Type what you hear, in kana |
| Grading | As §7.3 |
| Fallback | If audio unavailable/muted, exercise is swapped for §7.1 (see §11.5) |
| Applies to | Word, sentence |

### 7.9 Listening — comprehension

| | |
|---|---|
| Prompt | Audio sentence, no text shown |
| Input | Tap the matching English meaning (4 options) or matching image where available |
| Applies to | Sentence |

### 7.10 Kanji stroke order

| | |
|---|---|
| Prompt | Kanji with animated stroke order (KanjiVG paths) |
| Input | Tap-through animation, then a "which stroke comes next?" check |
| Grading | Correct stroke sequence identification |
| Note | **Recognition only, no handwriting input.** Full handwriting recognition is out of scope (§1.4). |
| Applies to | Kanji |

### 7.11 Kanji reading in context

| | |
|---|---|
| Prompt | A word containing the kanji, shown in kanji form |
| Input | Choose the correct reading from 4 kana options |
| Distractors | Other valid readings of the same kanji — this is the point of the exercise |
| Applies to | Kanji, word |

### 7.12 Matching pairs

| | |
|---|---|
| Prompt | Grid of 5 Japanese + 5 English tiles |
| Input | Tap to pair them |
| Grading | Per-pair; each pair produces its own SRS rating |
| Use | Efficient warm-up at the start of a session — 10 items in one screen |
| Applies to | Kana, word, kanji |

### 7.13 Reading comprehension

| | |
|---|---|
| Prompt | 2–4 sentence passage using only introduced items |
| Input | 2–3 comprehension questions, multiple choice |
| Availability | Stage 2+ only |
| Applies to | Sentence sets |

### 7.14 Speed round

| | |
|---|---|
| Prompt | Rapid-fire recognition, 5-second timer per item |
| Input | Tap (2 options only) |
| Purpose | Builds automaticity, which slow multiple-choice does not |
| SRS impact | **Does not feed the SRS scheduler.** Speed rounds test fluency, not recall strength, and would corrupt FSRS intervals. XP only. |
| Applies to | Kana, high-frequency words |

### 7.15 Teaching card (not graded)

| | |
|---|---|
| Content | New item introduction: the item, its readings, meaning, audio, mnemonic, stroke order, 1–2 example sentences |
| Input | "Got it" to continue |
| Purpose | Satisfies the teach-then-test principle (§1.5) |
| Effect | Creates the FSRS card in `New` state; the item becomes eligible for scheduling |

### 7.16 Exercise selection algorithm

For a given item and its current FSRS state, the generator picks an exercise type by weight:

| FSRS state | Preferred types | Rationale |
|---|---|---|
| `New` | 7.15 teaching card, then 7.1, 7.12 | Recognition first — easiest retrieval |
| `Learning` | 7.1, 7.2, 7.11, 7.12 | Both directions, low production load |
| `Review` (retrievability > 0.9) | 7.3, 7.4, 7.8, 7.14 | Harder retrieval where recall is strong |
| `Review` (retrievability < 0.7) | 7.1, 7.2 | Drop back to recognition to rebuild |
| `Relearning` | 7.15 abbreviated card, then 7.1 | Re-teach before re-testing |

Additional constraints: never show the same item twice within 3 exercises; never repeat the same exercise type more than twice consecutively; each lesson must contain at least three distinct types.

## 8. Spaced repetition engine

### 8.1 Algorithm choice

**FSRS (Free Spaced Repetition Scheduler), via [`ts-fsrs`](https://github.com/open-spaced-repetition/ts-fsrs).**

| Property | Value (verified) |
|---|---|
| Package | `ts-fsrs` |
| Licence | MIT |
| Algorithm version | FSRS v6 |
| Runtime | Node ≥ 20; ships ES modules, CommonJS and UMD |
| Core API | `createEmptyCard()`, `fsrs()`, `scheduler.repeat(card, date)`, `scheduler.next(card, date, rating)` |
| Optimizer | Separate package `@open-spaced-repetition/binding` (Rust-backed) for training parameters from review history |

Chosen over SM-2 because FSRS models memory as difficulty/stability/retrievability (DSR) and can be *optimised against the learner's own review history* — which matters a lot for a single-user app where thousands of reviews accumulate against one memory profile.

### 8.2 Card granularity

**One FSRS card per (item, direction) pair**, not per item. Recognition and production are genuinely different memories and decay at different rates.

| Item type | Cards created |
|---|---|
| Kana | `recognise` (kana→sound), `produce` (sound→kana) |
| Word | `recognise` (JP→EN), `produce` (EN→JP), `listen` (audio→meaning) |
| Kanji | `meaning`, `reading` |
| Grammar | `apply` (single card — pattern usage) |

This roughly triples card count versus per-item, but produces far more accurate scheduling. Estimated steady-state deck size for full N5: ~2,600 cards.

### 8.3 Scheduler configuration

| Parameter | Value | Rationale |
|---|---|---|
| `request_retention` | 0.90 | Standard default. Exposed in Settings (0.85–0.95) as "how much review am I willing to do." |
| `maximum_interval` | 365 days | Beyond a year is meaningless for a language being actively used |
| `enable_fuzz` | `true` | Prevents review clumping — items introduced together would otherwise come due together forever |
| `learning_steps` | `["1m", "10m"]` | Within-session relearning |
| `relearning_steps` | `["10m"]` | |
| Parameters | Start with `ts-fsrs` defaults | Re-optimise via the binding package once ≥ 1,000 reviews exist (§8.8) |

### 8.4 Rating mapping

FSRS takes four ratings: `Again` (1), `Hard` (2), `Good` (3), `Easy` (4). The app must map exercise outcomes to these **without asking the learner to self-rate** — self-rating is a friction point and beginners rate badly.

| Outcome | Rating |
|---|---|
| Wrong answer | `Again` |
| Correct but response time > 2× the learner's rolling median for that exercise type | `Hard` |
| Correct but only after using a hint | `Hard` |
| Correct, normal response time | `Good` |
| Correct, response time < 0.5× rolling median, on a `Review`-state card | `Easy` |
| Correct on a fuzzy/near-miss typed answer (§7.5) | `Hard` |

Rolling median is computed per exercise type over the last 50 responses, stored in the progress store. Until 20 samples exist for a type, default to `Good` on any correct answer.

### 8.5 Session composition

Every session mixes new material with due reviews. The ratio adapts to queue pressure:

| Due count | Session composition |
|---|---|
| 0–20 | 60% new lesson content, 40% review |
| 21–40 | 40% new, 60% review |
| 41–60 | 20% new, 80% review |
| > 60 | **100% review — new item introduction is paused** |

The pause is the key mechanism preventing the classic Anki death spiral. When paused, the UI says so plainly: *"Catching up on reviews — new lessons resume when your queue is under 60."*

### 8.6 Review ordering within a session

1. **Overdue first**, ordered by retrievability ascending (most-forgotten first)
2. **Lapsed items** (`Relearning` state) interleaved throughout, never clustered
3. **Never** two cards of the same item back-to-back (e.g. recognise then produce of the same word)
4. **Warm-up:** the first 3 exercises of any session are items with retrievability > 0.95 — starting with a win measurably reduces session abandonment

### 8.7 New-item throttle

Target: 5 new items/day at the chosen casual pace. Since each item creates 2–3 cards, this generates roughly 12 new cards/day, which at steady state produces a review load of roughly 40–60 cards/day — about 10–15 minutes. That is the whole basis of the pacing target.

The throttle is adaptive:

```
if (rolling7DayAccuracy < 0.80)      newItemsPerDay = max(2, current - 1)
else if (rolling7DayAccuracy > 0.92 && dueCount < 30)  newItemsPerDay = min(10, current + 1)
```

Manual override available in Settings, with a warning about the downstream review load.

### 8.8 Parameter optimisation

Once ≥ 1,000 reviews are logged, offer a one-tap "Tune my scheduler" action in Settings that runs the FSRS optimizer over the local review log and writes new parameters.

- Runs in a Web Worker to avoid blocking the UI.
- Keeps the previous parameter set so the change is revertible.
- Re-offer every 1,000 reviews thereafter.
- Requires the full review log to be retained — see §12.6, which is why review logs are never pruned.

### 8.9 Leech handling

An item that lapses 8 times is flagged a **leech**. On becoming a leech:

1. Suspend it from the review queue.
2. Surface it in a "Trouble spots" list on the home screen.
3. Offer three actions: *re-teach* (fresh teaching card, resets the FSRS card), *add my own mnemonic*, or *set aside* (suspend indefinitely).

Never silently keep drilling a leech. It burns time and morale.

## 9. Gamification

Full Duolingo-style treatment, with the dark patterns removed.

### 9.1 XP

| Action | XP |
|---|---|
| Correct answer, first attempt | 10 |
| Correct answer after a mistake | 4 |
| Lesson completed | 20 bonus |
| Perfect lesson (no mistakes) | 20 additional bonus |
| Unit test passed | 50 bonus |
| Daily goal met | 30 bonus |
| Review-only session completed | 25 bonus (deliberately generous — reviews are the valuable behaviour) |
| Speed round completed | 15 |

XP is cosmetic. It never gates content.

### 9.2 Levels

Level *n* requires cumulative XP of `100 × n^1.5`, rounded to the nearest 10. Level 1 → 2 costs 100 XP; level 20 → 21 costs about 1,840. Levels grant a title only (Beginner → Student → Apprentice → …) and a colour change on the profile ring.

### 9.3 Streaks

- A streak day counts when the daily XP goal is met.
- **Streak freeze:** auto-consumed on a missed day. Max 2 held. One is granted every 7 consecutive days, up to the cap.
- **Streak repair:** within 48 hours of breaking, a "repair" session (a review-only session of 20 exercises) restores the streak. Once per month.
- **Day boundary:** local midnight, using the device timezone, stored as a local date string (`YYYY-MM-DD`) not a UTC timestamp — see §15.6 for the timezone-change edge case.

The generosity here is deliberate. A broken streak is the single most common reason people abandon a learning app, and this app has no business model that benefits from anxiety.

### 9.4 Hearts (lives)

- 5 hearts maximum.
- **Lost only in lesson exercises**, never in reviews. Reviews are supposed to surface forgetting; punishing it is backwards.
- Regeneration: 1 heart per 30 minutes, or full refill by completing a "practice" session (10 review exercises).
- At 0 hearts: lessons are locked, but **review and practice remain fully available.** The learner can always study.

### 9.5 Daily goal

Four settings: Casual (30 XP), Regular (50 XP), Serious (100 XP), Intense (200 XP). Default **Casual** — matched to the stated 10–15 min/day. A ring on the home screen fills as XP accrues.

### 9.6 Badges

Roughly 30 badges across four families:

| Family | Examples |
|---|---|
| **Milestone** | First lesson, 100 words, 50 kanji, all hiragana, all katakana, Stage 1 complete |
| **Consistency** | 7/30/100/365-day streak, 10 weekend sessions, "Comeback" (returned after 7+ days away) |
| **Mastery** | 100 items at retrievability > 0.9, perfect unit test, 50 perfect lessons, zero leeches for 30 days |
| **Exploration** | Tried every exercise type, used stroke-order animation 50 times, tuned the scheduler |

Notably includes a **"Comeback"** badge for returning after a lapse — rewarding return rather than punishing absence.

### 9.7 The lesson map

The primary navigation surface. A vertical scrolling path of unit nodes, phone-shaped:

- **Node states:** locked (grey), available (colour + subtle pulse), in-progress (partial ring), complete (filled + check), needs-review (amber ring — from a failed unit test or decayed retrievability)
- A **"decay" indicator** on completed units whose average retrievability has fallen below 0.8, which taps straight into a targeted review session. This is the mechanic that makes the map honest about forgetting — Duolingo's map does not do this and it is the main reason its progress display overstates knowledge.
- Current position auto-scrolls into view on open.
- Stage boundaries are visual chapter breaks with a stage summary card.

## 10. Progress tracking and resume

This is the requirement the learner named explicitly, so it is specified tightly.

### 10.1 What "progress" means

Four independent layers, all persisted:

| Layer | Contains |
|---|---|
| **Item mastery** | Per-card FSRS state: stability, difficulty, due date, lapse count, review count |
| **Curriculum position** | Which lessons/units/stages are complete, in progress, or locked |
| **Session state** | The exercise sequence of an in-flight session and the answers given so far |
| **Meta** | XP, level, streak, hearts, badges, settings, statistics |

### 10.2 Progress views the learner can see

- **Home:** current streak, daily goal ring, due-review count, "continue" card
- **Lesson map:** unit-level completion and decay (§9.7)
- **Stats screen:** items known by type over time, review accuracy trend, review-load forecast for the next 30 days, heatmap of daily activity, retention audit result (§4.1)
- **Item browser:** searchable list of every item with its FSRS state, sortable by weakest-first. Includes the "Trouble spots" leech list.

The review-load forecast matters: seeing "you have 180 reviews due next Tuesday" *before* Tuesday is what lets a learner adjust the throttle in time.

### 10.3 Checkpointing

**Persist after every single answered exercise.** Not at lesson end, not on a timer, not on `beforeunload` (which is unreliable on mobile Safari).

Sequence per answer:
1. Grade the answer
2. Compute the FSRS update
3. Write to IndexedDB in one transaction: card update + review log entry + session state + XP delta
4. Only then advance the UI

The write is small (< 2 KB) and IndexedDB handles it in single-digit milliseconds. If the write fails, the UI shows a non-blocking warning and buffers to memory, retrying on the next answer.

Additionally listen for `visibilitychange` → `hidden` and flush, which is the reliable mobile signal.

### 10.4 The resume contract

**Requirement:** whatever happens — tab closed, phone dies, browser crashes, app updated, 3 weeks away — reopening the app returns the learner to exactly where they were, with zero lost answers.

Guarantees:

| Situation | Behaviour on reopen |
|---|---|
| Mid-lesson, closed the tab | Resume at the *next unanswered exercise* in the same session, with the same exercise sequence, same shuffled options, same XP-so-far. A "Resuming Lesson 3 — 7 of 15" banner appears. |
| Mid-lesson, > 24 hours ago | Offer a choice: resume the session, or discard and restart the lesson. Answers already given are kept in the review log regardless. |
| Mid-review-session | Resume remaining due cards. Cards already answered are not re-shown, even if they became due again. |
| App updated mid-session | Session state schema is versioned. If incompatible, gracefully complete the session as-is and log it, rather than dropping it. |
| Content updated mid-session | Session holds its own resolved copy of exercise data, so a content change never corrupts an in-flight session. |
| Returned after weeks away | Home screen shows a "Welcome back" state with the review backlog, a one-tap "ease me back in" session (30 easiest overdue items), and streak-repair options. |

**Implementation:** the session object stores the fully-resolved exercise list (including generated distractors and their order) at session start. Resume replays from `currentIndex`. It never re-generates the sequence, because regeneration would produce different distractors and break the "same session" guarantee.

### 10.5 Export and import

- **Export:** one tap → a single JSON file containing all four progress layers plus a schema version and export timestamp. Filename `nihongo-trail-backup-YYYY-MM-DD.json`.
- **Auto-export reminder:** every 30 days, a dismissible home-screen prompt.
- **Import:** file picker, validate the schema, show a diff summary ("this backup has 240 more reviews than your current data"), require explicit confirmation, then replace.
- **Format stability:** the export format is a public contract. Additive changes only; every version must remain importable.

### 10.6 Data safety

- IndexedDB can be evicted by the browser under storage pressure. Call `navigator.storage.persist()` on first launch and surface the result. If persistence is denied, show a one-time explainer recommending regular exports or enabling cloud sync.
- Keep a rolling in-app snapshot (the last 3 daily snapshots of the progress store) in a separate object store, so a corrupted write is recoverable without an external backup.
- Never destructive-migrate. Migrations write to a new store version and keep the old one until the new one validates.

## 11. Audio and listening

### 11.1 Requirement

Every word, sentence, and kana must be playable. Audio is not optional decoration — it is the difference between reading Japanese and knowing Japanese.

### 11.2 Source strategy — three tiers

| Tier | Source | Coverage | Notes |
|---|---|---|---|
| **1. Bundled recordings** | Tatoeba sentences that have audio | Partial | Tatoeba audio licence is **chosen per contributor and may be unspecified**, in which case it cannot be reused outside Tatoeba. The ingestion script must filter to explicitly-licensed audio only and record the licence per file. Do not assume audio is reusable. |
| **2. Pre-generated TTS** | Generate MP3/Opus at build time for all curriculum items using a TTS engine, bundle them | Full for vocabulary and kana | Preferred for reliability and offline use. Adds build-time cost and repo size (~30–60 MB for N5 scope at Opus 32 kbps). |
| **3. Runtime Web Speech API** | Browser `SpeechSynthesis` with a `ja-JP` voice | Fallback | Zero cost, zero bundle size, but **voice availability is inconsistent across browsers and platforms** and quality varies widely. Must be treated as a fallback, never the primary path. |

**Recommended:** Tier 2 as the primary path with Tier 3 as fallback. Tier 1 only where licensing is explicitly clear.

### 11.3 Audio requirements

- Format: Opus in WebM (primary), MP3 fallback for older Safari
- Normalised loudness across all files (target −16 LUFS)
- Playback speeds: 1.0× and 0.75× (0.75× must preserve pitch)
- Autoplay on exercise entry only when the learner has enabled it AND a prior user gesture exists in the session (mobile autoplay policy)
- A persistent replay button, large enough to hit one-handed

### 11.4 Pitch accent (optional, Stage 2+)

Display pitch-accent notation on vocabulary teaching cards where data is available. Not tested, not gated — present for exposure only. Source data would need to come from a supplementary dataset; treat as a stretch item and confirm licensing before including.

### 11.5 The silent-mode fallback

Since sound-off usage is expected (§2), the app must detect it and adapt:

- Detect via a silent-audio probe on session start, plus an explicit "I'm somewhere quiet" toggle.
- When silent, listening exercises (§7.8, §7.9) are **swapped**, not skipped — replaced with an equivalent recognition exercise on the same item so the SRS card still gets a rating.
- The listen-direction FSRS card is *not* rated by a swapped exercise; it is deferred to the next session with audio. Rating a listening card from a reading exercise would corrupt its stability estimate.

### 12.7 The storage abstraction (the Phase 5 hinge)

All persistence goes through one interface. Nothing else in the app imports Dexie.

```ts

  getCard(cardId: string): Promise<SrsCard | undefined>;
  upsertCards(cards: SrsCard[]): Promise<void>;

```

Two implementations ship: `IndexedDbProgressStore` (Phase 1) and later `SyncedProgressStore` (Phase 5) that wraps it. **This interface is the single most important architectural decision in the document** — get it right and cloud sync is additive; get it wrong and Phase 5 is a rewrite.

### 12.8 Sync-readiness fields

Even in Phase 1, every mutable record carries:

```ts
interface SyncMeta {
  updatedAt: string;      // ISO, always set on write
  deviceId: string;       // random uuid, generated once per install

```

Writing these from day one costs almost nothing and makes Phase 5 tractable.

### 12.9 Migrations

Dexie versioned schemas. Every migration must: run inside a transaction, write to the new version's stores, validate row counts against the old version, and only then mark the old version obsolete. Take a `snapshots` entry immediately before any migration.

### 13.3 The session engine

The heart of the app. Responsibilities, in order:

1. **Build** — given a session kind and current state, select items (§8.5), pick exercise types (§7.16), generate distractors, shuffle options, produce `ResolvedExercise[]`, persist the session
2. **Serve** — hand the current exercise to the UI
3. **Grade** — normalise input, compare, decide correctness (§7 per-type rules)
4. **Rate** — map outcome to an FSRS rating (§8.4)
5. **Schedule** — call `ts-fsrs`, update the card
6. **Persist** — one transaction: card + review log + session + meta (§10.3)
7. **Advance** — increment `currentIndex`, or finish

Rules: this module is pure logic with injected dependencies (store, clock, RNG). **The RNG must be seedable** so sessions are reproducible in tests and distractor generation is deterministic given a seed.

### 13.4 Content loading

- `manifest.json` fetched on boot, cached in the service worker
- `curriculum.json` and `kana.json` loaded eagerly
- Item shards loaded lazily on first reference, then held in an in-memory LRU (cap ~500 items) backed by the service-worker cache
- **Prefetch:** on lesson-map render, prefetch shards for the next 2 available lessons so starting a lesson is instant
- Stroke data and audio loaded per-item on demand, cached indefinitely

### 13.5 Offline behaviour

| Asset | Strategy |
|---|---|
| App shell (HTML/JS/CSS) | Precache, cache-first |
| `manifest.json` | Network-first with cache fallback (so content updates are picked up) |
| Content shards | Stale-while-revalidate |
| Audio | Cache-first, indefinite |
| Everything else | The app has no runtime network dependency in Phase 1 |

Offline is the default assumption, not a degraded mode. There is no "you are offline" error state in Phase 1 because nothing requires the network.

### 14.3 Key flows

**First launch:** Onboarding → hiragana Unit 0 Lesson 1 teaching cards → first exercises → session complete → home with streak = 1.

**Resume (the critical flow):** App open → `getActiveSession()` → if an active session exists and `lastActiveAt` < 24h, show the resume banner on Home and deep-link straight into the session at `currentIndex`. If ≥ 24h, present the resume-or-restart choice (§10.4).

### 15.1 Offline and installability

- Full functionality with no network after first load

### 15.2 Performance budgets

| Metric | Budget |
|---|---|
| Initial JS bundle (gzipped) | < 250 KB |
| Initial content payload (gzipped) | < 500 KB |
| Time to interactive on 4G, mid-range Android | < 3 s |
| Exercise-to-exercise transition | < 100 ms |
| Answer submit → feedback rendered | < 50 ms |
| IndexedDB write per answer | < 20 ms |
| Review queue build (2,600 cards) | < 200 ms |
| Sustained frame rate during animation | 60 fps |

Queue building must use the `due` index, not a full table scan.

### 15.3 Reliability

- Zero data loss on unexpected termination (§10.3)
- Corrupted-store recovery via snapshots (§10.6)
- Every storage write wrapped in error handling with a user-visible fallback path
- An error boundary per feature route so one crash cannot take down the app

### 15.4 Accessibility

- WCAG 2.1 AA colour contrast throughout
- Correct/incorrect never signalled by colour alone
- Full keyboard navigation on desktop: number keys select options, Enter checks/continues, Space replays audio
- Screen-reader labels on all interactive elements; `lang="ja"` on Japanese text so screen readers pronounce it correctly
- Minimum 44×44 px touch targets
- Respect `prefers-reduced-motion` and `prefers-color-scheme`
- Text scales with OS font-size settings without breaking layout

### 15.5 Japanese text handling (the fiddly part)

This deserves its own section because it is where most implementations get it wrong.

- **Romaji → kana IME:** a custom converter, not the OS IME. Must handle: `n` vs `nn` (ん), double consonants (`kk` → っ), long vowels (`ou`, `oo`, `ō`), `-` for ー in katakana, and all of Hepburn plus common Kunrei variants (`si`/`shi`, `ti`/`chi`, `tu`/`tsu`, `hu`/`fu`, `zi`/`ji`).
- **Answer normalisation:** strip whitespace, normalise full-width ↔ half-width, treat hiragana and katakana as equivalent for grading where appropriate, NFKC-normalise before comparison.
- **Furigana:** `<ruby>` markup generated from the token reading data in `SentenceItem.tokens`, with correct okurigana handling (食べる → 食(た)べる, not 食べる(たべる)).
- **Line breaking:** Japanese wraps mid-word; use `word-break: normal` with `line-break: strict` to avoid orphaned small kana and prohibited line-start characters (っゃゅょ、。).
- **Sorting:** gojūon order for kana lists, not Unicode code point order.
- **Counters:** number + counter combinations have irregular readings (一本 いっぽん, 三本 さんぼん). These need explicit data, not generation.

### 15.6 Time and timezone handling

- Streak days use the **local date string**, not UTC — a session at 23:30 local must count for that local day.
- FSRS due dates are stored as UTC ISO timestamps but compared against a "study day" boundary at local 04:00 (not midnight), so a late-night session does not accidentally skip a day's reviews.
- If the device timezone changes, never retroactively break a streak. If the change would break it, grant the day.

### 15.7 Privacy

No telemetry. No third-party requests at runtime. All data stays on device (Phase 1). If cloud sync is added, it is opt-in with an explicit explanation of what leaves the device.

## 16. Phased delivery plan

Each phase ships something usable. Do not start a phase until the previous phase's acceptance criteria pass.

### Phase 0 — Foundations

**Scope:** Repo setup, Vite + React + TS + Tailwind, Dexie schema, `ProgressStore` interface and IndexedDB implementation, `ts-fsrs` wrapper, seeded RNG, type definitions from §12, CI running lint + typecheck + unit tests.

**Acceptance:**
- `ProgressStore` has full unit test coverage against a fake IndexedDB
- An FSRS card can be created, rated, and scheduled, with results matching `ts-fsrs` reference behaviour
- A round-trip export → import produces byte-identical data

### Phase 1 — Kana MVP

**Scope:** Ingestion for kana only (hand-authored, no external dataset needed). Exercise types 7.1, 7.2, 7.3, 7.12, 7.15. Session engine with full checkpointing and resume. Stage 0 curriculum (hiragana + katakana). Home screen, session screen, session-complete screen. Basic XP and streak.

This is the first genuinely usable version — it can teach both kana scripts end to end.

**Acceptance:**
- Complete Stage 0 hiragana track without errors
- **Resume test:** kill the tab mid-lesson at 5 different points; every reopen resumes at the correct exercise with identical options and zero lost answers
- Due-card queue is correct after simulating 30 days of reviews with a fake clock
- Works fully offline after first load

### Phase 2 — Content pipeline and vocabulary

**Scope:** Full ingestion pipeline (§6.2) for JMdict, KANJIDIC2, KanjiVG, Tatoeba. Validation script with all §6.6 invariants. Curriculum generator. Shard loading and caching. TTS audio generation. Exercise types 7.4, 7.5, 7.8, 7.11. Stage 1 content.

**Acceptance:**
- `npm run content:build` produces a valid, validated content set from scratch
- All §6.6 invariants pass
- Initial content payload under the §15.2 budget
- Every Stage 1 item has playable audio
- Credits screen renders all required attributions

### Phase 3 — Full curriculum, grammar, gamification

**Scope:** Grammar authoring (~80 cards) and grammar exercise types 7.6, 7.7. Stages 2 and 3. Lesson map with decay indicators. Hearts, levels, badges, streak freezes and repair. Unit tests. Exercise types 7.9, 7.10, 7.13, 7.14.

**Acceptance:**
- Every N5 target item (§5.6) is reachable through the curriculum
- Sequencing rules hold across the entire curriculum
- All 30 badges are earnable, verified by a simulation test
- Lesson map decay indicator correctly reflects computed retrievability

### Phase 4 — Progress, insight, polish

**Scope:** Stats screen with all charts. Item browser and item detail. Trouble-spots/leech handling. Review-load forecast. FSRS parameter optimiser integration. Export/import UI. Accessibility audit and fixes. Performance tuning to budget. PWA polish and install flow.

**Acceptance:**
- Lighthouse: PWA pass, Performance ≥ 90, Accessibility ≥ 95
- All §15.2 budgets met on a mid-range Android device
- Scheduler tuning runs on 1,000+ simulated reviews and produces valid parameters
- Retention audit (§4.1) computes correctly against simulated history

### Phase 5 — Cloud sync (optional, only if actually needed)

**Scope:** `SyncedProgressStore` wrapping the local store. Backend: Supabase (Postgres + Auth) or equivalent. Single-user auth. Change-based sync using the §12.8 `SyncMeta` fields.

**Sync design:**
- **Last-write-wins per record** using `updatedAt`, with one exception: `reviewLog` is append-only and merges by union, never conflicts.
- **Cards:** if two devices reviewed the same card while offline, replay both review-log entries in timestamp order through FSRS to recompute the card. Do not merge card states directly.
- **Sessions:** device-scoped. An active session on device A does not sync to device B; only completed sessions sync.
- **Conflict surfacing:** anything unresolvable is reported to the learner rather than silently discarded.

**Acceptance:**
- Two devices, both offline, both reviewing → after sync, the review log is the union and every card state matches a from-scratch replay
- Sync failure never blocks local use
- Sync is entirely optional; the app functions identically with it disabled

| Level | Tool | Coverage |

## 18. Risks and open questions

### 18.1 Risks

| Risk | Impact | Mitigation |
|---|---|---|
| **Grammar authoring burden** (~80 explanation cards) is the real project bottleneck | Stalls Phase 3 | Draft with an LLM, then review each one manually. Ship Stage 1 grammar first; do not block on all 80. |
| Tatoeba sentence quality is uneven (community-contributed, some unnatural) | Learner internalises odd phrasing | Filter to sentences with high token overlap with introduced items, prefer sentences with audio, and manually review the Stage 0–1 set |
| Tatoeba audio licensing is per-contributor and often unspecified | Legal exposure | Ingestion script hard-filters to explicitly-licensed audio; default to generated TTS (§11.2) |
| Bundled audio grows the repo to 50 MB+ | Slow clone, slow first load | Opus at 32 kbps, lazy loading, service-worker caching; consider a separate asset host |
| Browser evicts IndexedDB | Total progress loss | `navigator.storage.persist()`, snapshots, export reminders (§10.6) |
| FSRS review load outgrows the 10–15 min budget | Learner falls behind and quits | Adaptive throttle (§8.7), 60-card pause threshold (§8.5), forecast visibility (§10.2) |
| Over-scoping — this document describes a large app | Never ships | Phase 1 (kana MVP) is genuinely useful alone. Ship it before touching Phase 2. |
| JLPT scope estimates are community guesses, not official | Curriculum may under- or over-shoot | Treat levels as tags (§5.6); make it easy to add items later |

### 18.2 Decisions deliberately deferred

- **Speaking practice** — requires speech recognition; browser support for Japanese ASR is inconsistent and cloud APIs cost money. Revisit after Phase 4.
- **Handwriting** — high implementation cost, and JLPT does not test handwriting.
- **Pitch accent testing** — display only in v1 (§11.4); testing it requires data quality the open datasets do not reliably provide.
- **N4+ content** — architecture supports it (§5.7); do not build it until N5 is complete.

### 18.3 Open questions for the owner

1. **Grammar authoring:** write the ~80 grammar cards yourself, generate-then-review with an LLM, or license/adapt an existing openly-licensed grammar reference? This is the biggest single content decision.
2. **Audio budget:** are you willing to spend a small amount (typically single-digit dollars) on a good cloud TTS for one-time build-time generation, or should this stay strictly zero-cost using open TTS models locally?
3. **Hosting:** self-host, or a free static host? Affects whether Phase 5 sync is realistic.
4. **JLPT deadline:** is there an actual exam date to work back from? If so, the pacing in §5.2 should be recalculated against it.
5. **Repo visibility:** public or private? Affects how carefully the share-alike obligations in §6.1 need to be documented.

## Appendix C — Glossary

| Term | Meaning |
|---|---|
| **FSRS** | Free Spaced Repetition Scheduler — modern SRS algorithm modelling difficulty, stability, retrievability |
| **Stability** | Days until recall probability falls to the retention target |
| **Difficulty** | How hard an item is for this specific learner (FSRS scale 1–10) |
| **Retrievability** | Current estimated probability of recalling an item right now |
| **Lapse** | A previously-learned item answered incorrectly |
| **Leech** | An item that has lapsed repeatedly (8× here) and is wasting study time |
| **Gojūon** | The 46-character base kana syllabary, in traditional order |
| **Dakuten / handakuten** | Voicing marks: が = か + dakuten; ぱ = は + handakuten |
| **Yōon** | Contracted sounds written with a small ゃゅょ, e.g. きょ |
| **Okurigana** | Kana following a kanji that complete a word, e.g. the べる in 食べる |
| **Furigana** | Small kana above kanji indicating the reading |
| **On/kun reading** | Chinese-derived vs native Japanese readings of a kanji |
| **JLPT** | Japanese-Language Proficiency Test; N5 is the entry level |
